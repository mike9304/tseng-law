# 公開專欄在全站搜尋的日期邊界

問題實際發生於網站自己的 `/api/search` 和搜尋來源收集器，與Google等外部搜尋引擎的索引時間不同。2026-10-02T23:16:22Z運營API回200/ok，查本篇完整標題仍未列出089。Studio執行時區是Asia/Seoul；Vercel通常使用UTC，但`new Date('2026-10-03')`本身在兩種環境都解讀成2026-10-03T00:00Z。本站檔案專欄使用臺灣讀者的發稿日，臺灣10月3日已開始，該合成UTC時刻卻尚未到，blog adapter因此把已公開正文誤當預約稿排除。

## 最小修正與界線

`listColumnBundles`僅在確實使用Markdown fallback、沒有CMS published override時，附上從該檔案取得的`filePublicationDate`；不從持久化CMS payload信任或推導此欄位。`listBlogPosts`以Asia/Taipei的當前日曆日期判定這種來源的發稿日。原frontmatter、publishedAt、dateDisplay、正文與圖片均不變，不把日期回填到昨天。

CMS文件仍按原`publishedAt`的精確時刻判斷。相同slug如果有已儲存的CMS版本，不能套用檔案日期；未公開草稿不納入；尚未到臺灣發稿日的檔案不納入。本次沒有新增白名單slug、跳過所有未來判斷、清空線上索引、變更排程API或修改任何影片。

既有搜尋索引五分鐘TTL保留。回歸測試先使用仍新鮮但缺文的索引，證明不會擅自重建；超過300000ms後真正執行來源收集並保存新索引，能在UTC午夜以前搜尋到089，再次查詢沿用新鮮索引。這段短暫快取等待與來源排除是兩個不同條件；不把五分鐘快取誤稱外部SEO延遲。
